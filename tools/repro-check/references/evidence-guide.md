# Evidence guide: where proof lives in a reproduction package

The rubric names what to decide; this file says where to look. Section
names below are the bundle's own headings in eval mode, and their live
equivalents on GitHub.

**The package's five surfaces.** In an eval bundle: `## Repo facts`
(the repo line, latest release, the `bug reports:` line naming what
the repo's template asks for, and the `contribution policy` line
including any AI policy), `## Issue` (title, body, labels, opener and
their association), `## Thread highlights` (maintainer and reporter
comments, often carrying the version the bug was confirmed on),
`## Candidate claim comment`, and `## Candidate repro report`. In live
mode: the issue page itself, its comment thread, `CONTRIBUTING.md` in
the repo root or `.github/` plus any `AI_POLICY.md` it links, the
repo's issue-template files, and the student's own draft comments as
the candidate side.

Read the issue first, then the drafts. The deciding evidence is almost
always the report's artifacts read back against the issue's own
description of the bug.

## Environment

**Where it lives.** The repro report's opening lines, usually an
`Environment:` line or a small table before the steps. The conditions
it must be read against live in two places: the issue body (which
often states the reporter's version and platform outright) and the
thread highlights (where a maintainer confirms the bug on a later
version, or narrows it to one platform). The repo-facts `latest
release:` line tells you what current means on the capture date. In
live mode: the same, plus the issue template's environment fields.

**What good looks like.** Two facts are load-bearing: the version of
the software under test, and the OS or platform it ran on. A single
line carries them as well as a formatted table —
`yq 4.53.3 (Homebrew), macOS 15.5 (arm64)` is a complete record. What
fails is a report that describes a machine instead of a version
("my high-end desktop", "long sessions on Windows 11"), or one that
names neither. Anything further the repo's template asks for —
install method, kernel, a related library's version — strengthens the
record where the bug plausibly depends on it, but its absence is never
disqualifying on its own. When the issue is platform-specific, the
platform detail the issue turns on (a driver, a shell, a backend) is
part of the environment, not an extra.

## Steps

**Where it lives.** The repro report's `Steps:` block — a numbered
list, a fenced shell transcript, or prose describing what was done.
Read it beside the issue's own reproduction steps, which the issue
body usually gives verbatim, and beside any refinement in the thread
("only happens with `--replace`", "needs the subdirectory layout").

**What good looks like.** A stranger holding the named environment and
nothing else could re-run the attempt from the package alone. Every
input is shown inline, generated by a command in the steps, or
publicly obtainable: a `printf` that writes the test file, the exact
command with its flags, the config file's contents. The failure mode
to watch for is a step that reaches outside the package — a private
monorepo, an internal config "I cannot share", a pre-commit hook only
the author has. Those reports may be entirely truthful and still prove
nothing a reader can check. Terseness is not the problem: four bare
shell lines with no prose around them can be perfectly followable.

## Behavior shown

**Where it lives.** The fenced output blocks, log excerpts, measured
numbers, or described screenshots inside the repro report, read
against the issue's description of what goes wrong — its error text,
its exit status, its symptom.

**What good looks like.** The artifact shows the issue's failure
signature, produced by the issue's trigger. Both halves matter, and
each fails in its own way. The trigger half fails when the run used a
different input or syntax than the issue named — a prefix range where
the issue is about an offset-from-end range, a colon where the issue's
input uses `=`, an expression edited until a variable is unbound. The
signature half fails when something went wrong but not the reported
thing: a graceful argument-validation error and exit 1 where the issue
reports a capacity-overflow abort and exit 101; a compile error where
the issue reports a runtime path error; garbled escape-sequence output
with the window still open and the prompt returning, where the issue
reports the terminal dying. Watch for the weakest form: an artifact
that shows only that the software starts — a version banner, a session
list, tabs rendering — which proves the setup, not the bug.

A control run is the strongest thing in this section when it is
present: the same steps with the suspect condition removed or shifted,
behaving differently. It converts "this failed near the trigger" into
"this failed because of the trigger."

## Honesty

**Where it lives.** The report's own summary sentences — `Expected:`,
`Actual:`, "Result:", "I can confirm" — read against the artifacts
printed directly above them, and its environment record read against
the target conditions from the issue and thread.

**What good looks like.** The stated outcome claims exactly what the
artifacts show and no more. Three shapes recur:

- *Honest reproduction.* The report says the bug appeared and the
  artifact shows the issue's failure signature. The expected and
  actual statements match what is printed above them, rather than
  inverting it or describing something the output does not contain.
- *Honest cannot-reproduce.* The report says the bug did not appear,
  shows the attempt it actually made, and names what differed from the
  reporter's conditions along with what a triggering setup might need.
  This is a complete, postable result — it is not a failure, and the
  rubric treats it as a pass when the attempt exercised the trigger.
- *Overclaim.* Confidence exceeding evidence: "guaranteed
  reproducible" with no measurement behind it, a root cause diagnosed
  with no artifact showing it, or a narrated crash the transcript
  contradicts.

Deviation is the quiet case. A run on a different version or platform
than the issue was confirmed on is fine when the package names it —
"filed against 13.0.0; behavior is unchanged on 15.2.0" is one
sentence and it is enough. Silence about it is not. The direction
matters: testing newer than the confirmed version and saying so is
ordinary practice, while testing *older* than the version the issue
was confirmed on produces an artifact that may only be that old
version's behavior, so naming it does not by itself make it evidence.

## Comms

**Where it lives.** The candidate claim comment, read against the
issue it would be posted on; and both drafts read against the
repo-facts `contribution policy` line — in live mode, `CONTRIBUTING.md`
and any `AI_POLICY.md` it links, plus AI-disclosure checkboxes in the
issue or PR templates.

**What good looks like.** The claim comment could only have been
written for this issue: it names the behavior, the version reproduced
on, the file it will read, or the thread's pointer, and it says what
the author will do next. Boilerplate is the tell — a comment that
would read identically on any other issue in any other repo, a `+1`
with no stated intent, or a self-assignment with nothing concrete
behind it. Honest scope is the other half: no delivery deadline, no
guaranteed fix, no request to reserve the issue. Stating inexperience
plainly costs nothing and is not a failure.

On AI policy, read what the policy actually covers before deciding
anything. Treat course packages as AI-assisted work, then place the
repo in one of three groups. *Silent* — no stated policy — needs no
disclosure. *Permissive* — AI welcome, the contributor is responsible
for understanding the work — needs no disclosure either, and a policy
that asks for disclosure only in pull requests belongs here when the
package is an issue comment. *Disclosure-requiring* — the policy asks
that AI use be disclosed in comments, or that all AI usage in any form
be disclosed — needs the comment to name the tool and the extent of
its help. A package can be flawless proof and still be unpostable on
this surface alone, which is exactly why the policy line is read
before the comment is judged.
