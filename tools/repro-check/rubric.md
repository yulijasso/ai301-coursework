# Rubric: is this reproduction package ready to post?

The package is the claim comment plus the repro report, read against
the issue they belong to. Grade the proof, never the prose: a terse
complete report is ready, a long confident one can be empty.

## Terms used below

- **Artifact** — an output excerpt, log, measurement, or described
  screenshot produced by running the steps. Narration of what the
  author saw is not an artifact.
- **Trigger** — the input, command, syntax, or condition the issue
  names as producing the bug.
- **Failure signature** — the specific error text, exit status, panic,
  or observable symptom the issue reports.
- **Target conditions** — the versions, platform, and setup the issue
  and its thread state the bug was confirmed on.

**Claim-side checks** — gradable from the claim comment and the
repo-facts block alone: `claim-specific`, `claim-honest`,
`ai-disclosure`. Every other check needs the repro report, so on a
claim-only live draft those are the checks reported `unclear`.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `env-recorded` | The repro report's environment record, read against the software and platform the issue concerns. | The report names (a) the version of the software under test and (b) the operating system or platform it ran on. One line carries this as well as a table does. Fails if either is missing — including a report that describes a machine ("my high-end desktop", "long sessions on Windows 11") without naming the version under test. Detail the repo's template asks for beyond these two (install method, kernel, related library versions) strengthens the record but is never required. | required |
| `steps-followable` | The repro report's steps and inputs, read as a stranger who has the named environment and nothing else. | A stranger could re-run the attempt from what the package itself contains. Fails if any of: (a) a step depends on something the reader cannot obtain — a private repository, an unshared config, an internal hook; (b) an input is referred to but not shown inline, generated by a command in the steps, or publicly obtainable; (c) the steps omit a condition the issue names as part of the trigger. | required |
| `artifact-present` | The repro report's body: output excerpts, logs, measurements, or described screenshots, as distinct from its assertions. | The report contains at least one artifact. Assertion is not artifact: "can confirm", "it reproduces every time", "I verified this race condition" are claims about evidence, not evidence. Fails if the report's only content is narration with nothing shown. | required |
| `outcome-matches-artifact` | The report's stated outcome (what it says happened) read against its own artifacts, and both read against the behavior the issue describes. | The stated outcome does not claim more than the artifacts show. **If the report claims reproduction,** it fails if any of: (a) the steps use a different input, syntax, or command than the issue's trigger; (b) the artifact shows a different failure than the issue's failure signature — a graceful validation error where a panic was reported, a compile error where a runtime error was reported; (c) the issue reports a crash, panic, process death, or nonzero exit and the artifact shows the process surviving — output still flowing, the prompt returning, the window still open; (d) the artifact shows only that the software starts and runs. **If the report states it could not reproduce,** it passes when the artifact shows a real attempt that exercised the issue's trigger; showing the failure is not required. An evidenced cannot-reproduce is a pass. | required |
| `deviation-named` | The environment record and steps, read against the target conditions stated in the issue and its thread. | Either the attempt matches the target conditions, or every difference is named in the package — one sentence giving the version or platform used and how it differs. Fails if any of: (a) a difference from the target conditions goes unstated; (b) the run used a version older than one the issue was confirmed on and the report neither shows the behavior persisting on a confirmed version nor says why the older version is relevant. Naming an older-version run is not enough on its own: that artifact may be the old version's behavior rather than evidence about the reported bug. | required |
| `claim-specific` | The candidate claim comment, read against the issue it is posted on. | The comment shows it was written for this issue — it names the behavior, the version, the file, or the thread's pointer — and states what the author will do next. Fails if any of: (a) it would read identically on any other issue ("great project, this looks like a good one for me"); (b) it is a me-too or +1 with no stated intent; (c) it announces interest or self-assignment without naming a concrete next step. | required |
| `claim-honest` | The candidate claim comment, read against what the package's own evidence supports. | The comment promises nothing it cannot keep and asserts nothing its evidence does not support. Fails if any of: (a) it gives a delivery deadline or guarantees a fix; (b) it asks for the issue to be reserved, locked, or held; (c) it states a certainty the package does not back — "guaranteed reproducible", a root cause asserted with no artifact showing it. | required |
| `ai-disclosure` | The repo-facts block's contribution and AI policy, read against what the claim comment and repro report disclose. Course packages are AI-assisted work. | Passes if any of: (a) the repo states no AI policy; (b) its policy permits AI assistance without asking for disclosure; (c) its policy scopes disclosure to pull requests only. When the stated policy asks that AI use be disclosed in issue comments — including a policy requiring all AI usage in any form to be disclosed — the comment must name the tool and the extent of its help. Fails when such a policy is stated and neither comment discloses, however strong the proof is. | required |
| `control-run` | The repro report's artifacts. | A second run isolates the trigger: the same steps with the suspect condition removed or shifted, shown to behave differently. This is what separates "the bug is here" from "something failed while I was nearby." | preferred |
| `expected-vs-actual` | The report's stated expected and actual results, read against the artifact printed above them. | The report states what it expected and what it actually observed, and both are consistent with that artifact. Fails if the stated result contradicts or inverts the artifact — an "actual" describing something the output does not show, or an "expected" that restates the bug as the desired outcome. | preferred |

## Verdict rule

Accept — ready to post — only if every `required` check passes. A fail
on any one of them is a reject: the package is held, not posted.

`unclear` on a required check counts as a fail, with one exception the
skill itself defines: on a claim-only live draft, the checks that need
the repro report are reported `unclear` with the reason `not yet
applicable: claim-only draft` and are left out of this rule entirely —
the verdict then answers only whether the claim comment is ready. The
claim-side checks named above still gate that verdict. Outside that
case, proof I cannot verify is proof that is not ready to post.

`preferred` checks never change the verdict. Report their grades; they
say how much stronger a package is than the minimum it had to clear.
